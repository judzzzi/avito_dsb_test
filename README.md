# Кандидатогенерация для поиска услуг Авито

Для каждого запроса из benchmark_queries нужно вернуть до 50 объявлений из корпуса
(189 212 шт.), метрика Recall@50.

Результат: 0.89 на бенчмарке, 0.923 на моей локальной валидации. Валидация
получилась оптимистичнее бенчмарка. Скорее всего, дело в том, что около 9% запросов
бенчмарка пришли из поиска по всем категориям (search_category = 0). В train таких
почти нет, поэтому в валидацию они не попали.

## Как запустить

```bash
pip install -r requirements.txt
# train.parquet, benchmark_queries.parquet, benchmark_items.parquet положить в ./data
bash run_all.sh   # в конце появится answer.csv
```

Всё считается локально на CPU, внешние API и предобученные модели не нужны.
Прогон занимает примерно 30 минут, памяти нужно около 4 ГБ.

## Как устроено

Решение работает в два этапа. Сначала несколько простых источников набирают
для запроса около 400 кандидатов, потом LightGBM (lambdarank) выбирает из них 50.

Главное, что я заметил в данных: очень сильно влияет локация. Один BM25 даёт
0.39, а BM25 плюс вероятность локации — уже 0.81. Просто фильтровать по городу
нельзя: у части запросов локация «Москва и область» или «вся Россия», а объявлений
с такой локацией нет. Поэтому я считаю по логам P(локация объявления | локация поиска)
и сглаживаю её по расстоянию между городами. Ко всем скорам источников добавляется
2·log P(локация), коэффициент 2 подобрал на валидации.

Источники кандидатов (candidates.py):

- `all` — BM25 по заголовку (с весом 2), параметрам и описанию, top-200;
- `title` — BM25 только по заголовку, top-100;
- `prof` — берём похожие запросы из логов (по символьным n-граммам) и слова
  из заголовков объявлений, которые по ним выбирали, top-100;
- `tr` — словарь «слово запроса → слово заголовка», собранный по логам, top-100;
- `hist` — объявления, которые выбирали по этому или похожему запросу, top-50;
- `mc` — популярные объявления самой вероятной микрокатегории, top-50;
- `emb` — косинус эмбеддингов своей двухбашенной модели, top-100.

Двухбашенная модель (embed.py) простая, в духе fastText. На вход идут стемы слов
и символьные 3-граммы, всё хэшируется в 2^19 корзин, дальше EmbeddingBag
размерности 128 и линейная голова на каждую башню. Обучается с нуля на парах
«запрос → выбранное объявление», функция потерь — softmax по батчу. Пары с тем же
текстом запроса внутри батча не считаются негативами. На CPU 5 эпох проходят
за несколько минут.

Признаки ранкера (около 70): BM25 по полям, доля покрытых слов запроса, всё про
локацию (вероятность, совпадение, расстояние), вероятность микрокатегории по логам,
история объявления, совпадение с фильтрами «Вид услуги»/«Тип услуги», рейтинг,
отзывы, цена, косинус эмбеддингов, а ещё ранги и доли от максимума внутри запроса.

Тексты привожу к нижнему регистру, ё заменяю на е, стеммлю через PyStemmer
(Snowball), убираю стоп-слова. BM25 написан на scipy.sparse (bm25.py).

## Валидация

split.py собирает из train что-то похожее на бенчмарк. Корпус того же размера,
около 10% его объявлений встречаются в логах (как в бенчмарке). Запросы — 9000
событий с уникальными текстами: на 6000 обучается ранкер, на 3000 считается
Recall@50. Модели и статистики строятся только по оставшейся части train, чтобы
не было утечки.

| Что | Recall@50 (валидация) |
|---|---|
| BM25 по всему тексту | 0.394 |
| BM25 + вероятность локации | 0.807 |
| + все источники кандидатов | 0.828 |
| + ранкер LightGBM | 0.907 |
| + эмбеддинги как источник и признаки | 0.923 |
| потолок (полнота всех кандидатов) | 0.968 |

## Порядок шагов (run_all.sh)

1. `prep.py` — стемминг, общая таблица объявлений;
2. `split.py` — локальная валидация;
3. `embed.py val` — эмбеддинги, обученные на части train для валидации;
4. `build_val_cands.py` — кандидаты и признаки для валидации;
5. `train_ranker.py` — обучение ранкера и оценка;
6. `train_ranker.py --final` — ранкер на всех валидационных запросах;
7. `embed.py full` — эмбеддинги, обученные на всём train;
8. `predict.py` — кандидаты для бенчмарка, answer.csv и проверка формата.

Сиды везде зафиксированы.

## Библиотеки

pandas, numpy, pyarrow, scipy, scikit-learn, PyStemmer, LightGBM, PyTorch.
Предобученные модели не использовались.

## Что можно улучшить

- Добавить дообученный предобученный энкодер (например, multilingual-e5-small).
  Я его попробовал: даже без дообучения он находит нужные объявления чуть лучше
  моей двухбашенной модели, но встроить в решение не успел.
- Сделать валидацию ближе к бенчмарку, в первую очередь с учётом запросов
  из поиска по всем категориям.
- Обучать ранкер на нескольких разбиениях валидации.
