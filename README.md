# Кандидатогенерация для поиска услуг Авито (Recall@50)

Решение отбирает для каждого запроса бенчмарка до 50 объявлений из корпуса
(189 212 шт.). Схема двухступенчатая:

1. Несколько быстрых источников кандидатов дают для запроса объединение
   из примерно 350 объявлений. Полнота такого объединения на валидации ≈ 0.957.
2. Ранкер LightGBM (lambdarank) по ~60 признакам выбирает из объединения итоговые 50.

| Вариант (локальная валидация, 3000 запросов) | Recall@50 |
|---|---|
| BM25 по всему тексту объявления | 0.394 |
| BM25 + вероятность локации, выученная по логам | 0.807 |
| + объединение источников кандидатов | 0.828 |
| **+ ранкер LightGBM (итоговое решение)** | **0.907** |
| Потолок: полнота объединения кандидатов | 0.957 |

Всё работает локально на CPU: нет внешних API и скачиваемых моделей.
Полный прогон занимает около 15 минут на 2 ядрах, пик памяти около 4 ГБ.

## Ключевые наблюдения из данных

* **Локация — главный фактор.** В 91% случаев при поиске в городе выбирают
  объявление из того же города. У ~16% запросов локация «региональная»:
  Москва + МО, СПб + ЛО, вся Россия. Объявлений с такой локацией нет вообще,
  поэтому просто фильтровать по совпадению локации нельзя. Решение:
  P(локация объявления | локация поиска) считается по логам train
  и сглаживается геодистанцией между центроидами локаций.
* **Логи почти не пересекаются с корпусом.** В train есть только ~10% объявлений
  корпуса и ~37% текстов запросов бенчмарка. Поэтому запоминание пар
  «запрос → объявление» почти не помогает. Из логов берутся обобщаемые знания:
  какие слова заголовков стоят за словами запросов, какие микрокатегории
  и локации выбирают.
* **Фильтры запроса надёжны.** «Вид услуги» и «Тип услуги» совпадают
  с параметрами выбранного объявления в 93–99% случаев. Это сильный признак,
  но не жёсткий фильтр.

## Локальная валидация (`split.py`)

Валидация повторяет устройство бенчмарка по train:

* Объявления train делятся по хэшу id на группы A (55%) и B.
* Валидационный корпус: 170k объявлений из A и 19k из B, всего 189 212,
  как в бенчмарке. Как и там, ~10% объявлений корпуса есть в логах.
* Запросы: 9000 поисковых событий (текст + локация + фильтры) с уникальными
  текстами, все выбранные объявления которых лежат в корпусе.
* Логи (fit): строки train без объявлений группы A и без валидационных событий.
  Получилось ~41% запросов, чьи тексты есть в логах (в бенчмарке 37%).
* 6000 запросов идут на обучение ранкера, 3000 — на оценку Recall@50.

## Источники кандидатов (`candidates.py`)

К текстовому скору каждого источника добавляется `2 · log P(локация)`.
Коэффициент 2 подобран на валидации.

| Источник | Что делает | Top-K |
|---|---|---|
| `all` | BM25 по заголовку ×2, параметрам и описанию | 200 |
| `title` | BM25 только по заголовку | 100 |
| `prof` | Профиль запроса: берём ближайшие по символьным 3–5-граммам запросы из логов и слова из заголовков выбранных ими объявлений (расширение запроса по логам) | 100 |
| `tr` | Словарь перевода «слово запроса → слово заголовка», обученный по логам: P(w\|t)·log lift | 100 |
| `hist` | Объявления, которые выбирали по этому или похожим запросам | 50 |
| `mc` | Популярные рядом объявления наиболее вероятной микрокатегории | 50 |

Тексты нормализуются: нижний регистр, ё→е. Затем стемминг Snowball (PyStemmer)
и удаление стоп-слов. BM25 реализован на `scipy.sparse`, файл `bm25.py`.

## Признаки ранкера

* **Текст:**
  * BM25 по каждому полю, по профилю и по переводу;
  * idf-взвешенная доля покрытых терминов запроса;
  * ранги и доли от максимума внутри запроса.
* **Локация:** P(лок. объявления | лок. поиска), совпадение локаций,
  расстояние в км, «региональность» локации поиска.
* **Логи:**
  * вероятность микрокатегории объявления по похожим запросам;
  * история объявления: популярность, выбор по такому же или похожему запросу;
  * близость к ближайшему запросу из логов.
* **Фильтры:** доля выполненных условий «Вид/Тип услуги».
* **Объявление:** рейтинг, отзывы, цена, флаги телефона и сообщений,
  длина текста.
* **Запрос:** число слов, суммарный idf, число кандидатов,
  из каких источников пришёл кандидат.

Самые важные признаки: базовый скор `BM25 + 2·log P(лок)` и его ранг, профиль
по логам, расстояние, покрытие терминов, вероятность микрокатегории,
совпадение фильтров.

## Как запустить

```bash
pip install -r requirements.txt
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в ./data
bash run_all.sh        # -> answer.csv
```

`run_all.sh` по шагам:

| Шаг | Скрипт | Что делает |
|---|---|---|
| 1 | `prep.py` | Стемминг текстов, единая таблица объявлений → `work/` |
| 2 | `split.py` | Локальная валидация (корпус, запросы, логи) |
| 3 | `build_val_cands.py` | Кандидаты и признаки для валидации, печатает полноту источников и бейзлайн |
| 4 | `train_ranker.py` | Обучение на части rank, оценка Recall@50 на части eval |
| 5 | `train_ranker.py --final` | Финальный ранкер на всех валидационных запросах |
| 6 | `predict.py` | Контекст по всему train и корпусу бенчмарка → `answer.csv` с проверкой формата |

Все случайности фиксированы: seed и детерминированный хэш.

## Использованные open-source библиотеки

* pandas, numpy, pyarrow — данные;
* scipy (разреженные матрицы) и scikit-learn (CountVectorizer, TfidfVectorizer) —
  BM25 и символьные n-граммы;
* PyStemmer — Snowball-стеммер для русского и английского;
* LightGBM — ранкер lambdarank.

Предобученные модели не используются.

## Что можно улучшить

* Дообучить на логах плотный энкодер (e5, USER-bge-m3) и добавить его как
  источник и признак. Это закроет семантические промахи вроде
  «чистка пяток» → «Подолог». В этом окружении не было доступа к Hugging Face
  и GPU.
* Сделать несколько разбиений валидации (`split.py <id>`), чтобы у ранкера было
  больше данных, а оценка стала стабильнее.
